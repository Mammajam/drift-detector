The problem

Small mismatches pile up between the Figma file and production.

Designers hand off pixel-precise frames. The build drifts a few pixels at a time: a padding rounded down, a font weight swapped, a colour that's close but not the token. Nobody catches it until a design QA pass days later, when finding the cause means flicking between two windows and guessing.

That pass is slow, subjective and repeated on every release. Feedback lands as screenshots in chat with no link to the exact build or line of code, and fixes get lost. The cost is time for both roles and a product that slowly stops matching its own design system.

Who it's for

Two roles, one shared view of the truth.

Product designer "I spend release week screenshotting the staging site and drawing red circles."
  • Needs: proof of what drifted, on which build
  • Wants: to sign off with confidence, not by eye
Frontend developer "Tell me the exact value and where. 'Feels off' isn't a ticket."
  • Needs: precise spec values: px, weight, token name
  • Wants: feedback tied to the pull request they're on

Proto-personas built from common handoff pain points. Validate with 5 short interviews (3 designers, 2 developers) on days 1–2.

Core flow

From pull request to sign-off in four steps.

  1. Link

    Connect a Figma frame to a route, such as /pricing, in the project.

  2. Capture

    Each Deployxa preview deploy is captured at matching breakpoints.

  3. Compare

    Overlay, difference and side-by-side views; drift is auto-flagged as pins with spec values.

  4. Resolve

    Pins become tickets on the pull request. The next preview re-checks them, and the designer signs off.

Theme context and switching

One set of tokens, three theme states, and drift checks in both themes.

The app offers Light, Dark and System. System follows the operating system and is the default. A React ThemeContext holds the choice, works out the actual theme, and writes it to <html data-theme>. Every component reads colours only from CSS tokens, so switching themes never re-renders component styles.

  • No flash on load: a tiny inline script in <head> applies the saved theme before the first paint.
  • Saved per user: the choice is kept in localStorage, and also in the user's profile in Postgres so it follows them across devices.
  • Fixed meaning in both themes: blue = design, amber = build, rose = drift. Each is tuned per theme to keep AA contrast.
  • Theme-aware drift: each Deployxa preview is captured twice, in light and dark (Playwright colorScheme). Each capture is compared to the matching Figma variable mode, so a dark-mode-only colour bug becomes its own ticket.

This page uses the same pattern. Try the Light / Dark / System switch at the top.

// app/theme-provider.tsx
type Choice = 'light' | 'dark' | 'system';
const ThemeCtx = createContext<{
  choice: Choice; resolved: 'light'|'dark';
  setChoice: (c: Choice) => void;
} | null>(null);

export function ThemeProvider({ children }) {
  const [choice, setChoice] = useState<Choice>(
    () => (safeGet('dd-theme') as Choice) ?? 'system');
  const osDark = useMediaQuery('(prefers-color-scheme: dark)');
  const resolved = choice === 'system'
    ? (osDark ? 'dark' : 'light') : choice;

  useEffect(() => {
    const root = document.documentElement;
    choice === 'system'
      ? root.removeAttribute('data-theme')
      : root.setAttribute('data-theme', choice);
    safeSet('dd-theme', choice);
  }, [choice]);

  return <ThemeCtx.Provider value={{ choice, resolved, setChoice }}>
    {children}</ThemeCtx.Provider>;
}
export const useTheme = () => useContext(ThemeCtx)!;
Accessibility

Inclusive by construction.

  • Every visual pin is mirrored in a text list that a keyboard and screen reader can use.
  • Drift is never signalled by colour alone: each flag has a number, shape and label.
  • The opacity slider and mode switch are native controls with visible focus.
  • Text meets WCAG AA contrast in both light and dark themes.
  • Animation is turned off for users who set reduced motion.
  • The tool also flags contrast drift: a build colour that fails AA where the design passed.

Risks and fallbacks

  • Chromium on the host: if Playwright can't run in Deployxa's Node runtime, put the capture worker in its own container service. Deployxa lists multi-container apps.
  • Automatic triggering: if Deployxa doesn't expose deploy events, take the preview URL from the pull request or let users paste it.
  • Scope: pixel diff and pins are the MVP. Matching each mismatch to an exact style value (padding, font weight) is a stretch goal.
Success targets

How we'll know it works.

Faster QA

Time from preview deploy to designer sign-off, measured in a timed comparison against a manual review in usability tests.

Fewer rounds

Design QA back-and-forth per feature, with drift resolved before merge instead of after release.

Exact feedback

Share of tickets that carry an expected and an actual value, so developers rarely need to ask.
